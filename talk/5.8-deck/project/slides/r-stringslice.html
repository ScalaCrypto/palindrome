For the Q&A, if someone asks why the slices can't share instead of copying. They can: this is java.lang.String's own old trick. Until Java 7u6 a String had an offset and a count, and substring shared the parent's char array. Java dropped it because a three-character substring kept a hundred-megabyte parent alive, and this class brings that trade-off back. It works for any IndexedSeq: a String (as a WrappedString), an ArraySeq or a Vector, and the unchanged 3.9 isPalindrome becomes O(n) on all of them. With it, the check on a 40,000-character String takes under a tenth of a millisecond, against 0.6 to 1.3 seconds through WrappedString, and it's about as fast over an ArraySeq or a Vector. But it's opt-in: "racecar".isPalindrome still goes through Predef's WrappedString, so you write IndexedSeqSlice(xs, 0, xs.length).isPalindrome. It doesn't help a List, where reaching the last element is O(n) anyway: convert it once with toIndexedSeq. Why not s.view? A view doesn't match the standard +: and :+, because it isn't a Seq. You can write extractors that do match views, but a view's drop wraps the previous view instead of moving its bounds, so every access walks through all the layers: still O(n²), and on a Vector far slower than without the view. The slide leaves out bounds checks, which is enough for isPalindrome but not for a general-purpose class. The index loop on the previous slide is still the simpler answer.
