Reserve · “Can palindromize be linear?”

Knuth–Morris–Pratt in O(n)

extension [Repr: IsSeq as seq](xs: Repr)

  def palindromize(using eq: Eq[seq.A], bf: BuildFrom[Repr, seq.A, Repr]): Repr =

    val s = seq(xs).toIndexedSeq

    val r = s.reverse                      // a palindromic suffix of s is a prefix of r

    val border = new Array[Int](r.length)  // the longest border of each prefix of r

    var k = 0

    for i <- 1 until r.length do

      while k > 0 && !eq.eqv(r(i), r(k)) do k = border(k - 1)

      if eq.eqv(r(i), r(k)) then k += 1

      border(i) = k

    k = 0                                  // match r along s: k ends as that longest prefix

    for x <- s do

      while k > 0 && !eq.eqv(x, r(k)) do k = border(k - 1)

      if eq.eqv(x, r(k)) then k += 1

    bf.fromSpecific(xs)(s.iterator ++ s.take(s.length - k).reverseIterator)

For the Q&A, if someone asks whether palindromize can be linear. It can: the longest palindromic suffix of s is the longest suffix of s that's also a prefix of s.reverse, and Knuth–Morris–Pratt string matching (1977) finds that in one pass over each, comparing only through Eq, so a case-insensitive Eq still works (it needs Eq to be an equivalence, which both instances are). O(n) time and O(n) memory, against the repo's O(n²) search, which also allocates a new middle at every step of every check. On a 40,000-character String, 20,000 a's, a b, then 19,999 a's, this takes 19 ms and the repo's version 7.4 s (one run each on Scala 3.9, JDK 21; not JMH). It agrees with the repo's version on all 9,841 strings over a, b and c up to length 8. It's not in the code for the same reason as the index loop: fifteen lines of index and table code make an algorithm point, not a language one.
